# User

`User` represents a registered account. Its UUID is the stable identity for future
word ownership and review history; email can change without changing ownership.

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | UUID, primary key | Generated by the application when inserted. |
| `email` | string (320), required, unique | Account email. Future registration must trim and normalize it consistently before storage and lookup. |
| `password_hash` | nullable string (1024) | Encoded password hash, including algorithm and salt; never a plaintext password. |
| `auth_provider_id` | nullable string (512), unique | Trusted provider identity, namespaced by provider/issuer to avoid subject collisions. |
| `created_at` | timestamp with time zone, required | Database-generated account creation time. |
| `disabled_at` | nullable timestamp with time zone | Set when access is disabled; clearing it permits reactivation if not deleted. |
| `deleted_at` | nullable timestamp with time zone | Set for soft deletion. |

At least one of `password_hash` or `auth_provider_id` must be present and nonblank.
Both may be present for an account with linked authentication methods. Provider
identities must come from verified authentication results, not client assertions.
Email cannot be blank; case normalization and email syntax validation belong to
the future account service. Database email uniqueness currently compares stored
values, so callers must use the same normalization for every write.

An account is active only when both lifecycle timestamps are null. A deleted
account must be denied access even if `disabled_at` is null. Soft deletion retains
identity and email uniqueness; it is not data erasure. Authentication enforcement,
password hashing, account APIs, and retention/erasure policy are separate work.
Hashes and provider identifiers must never appear in public API responses.

Implementation: `backend/app/models/user.py`; migration: `0002_users`.
